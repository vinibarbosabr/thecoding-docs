# Documentation Engineering

Clear, accurate documentation is one of the highest-leverage investments a technical team can make — and one of the easiest to under-invest in.

I help teams turn complex products and protocols into documentation that developers can actually understand, use, and share: well-structured, technically precise, practical, and ready for both humans and LLMs.

The focus is always the same: reduce friction for users and builders and make your product easier to understand, use, integrate, and trust.

<Tip>
  Available for one-off Health Checks, focused section rebuilds, or ongoing part-time ownership.
</Tip>

## Docs-as-Code Engagement

I work with **docs-as-code** principles and treat documentation as an essential product surface.

Typical work includes:

- Reviewing and improving existing documentation through pull requests
- Fixing broken or outdated flows and adding practical examples
- Rebuilding high-value sections (Getting Started, core concepts, key integrations)
- Improving structure and clarity for both human readers and LLMs
- Aligning documentation with the actual code and product behavior
- Ongoing ownership so docs stay accurate as the product evolves

I read the code, test the flows, and implement the improvements myself.

## Engagement models explained

### 1. Docs Health Check + Quick Wins

I review the **entire** documentation surface, with special attention to the most important journeys (Getting Started, core concepts, main integrations).

I then implement the highest-leverage improvements that can be done relatively quickly through pull requests. Typical work includes:

- Fixing broken or outdated steps
- Adding practical code examples
- Improving clarity and structure
- Better alignment between code and docs
- Making key pages more self-contained and LLM-friendly

This is **breadth + prioritized implementation**. It is not a full rewrite of major sections.

### 2. Focused Section Rebuild

We deliberately choose 1–3 high-value sections. I go deep on those sections only:

- Thorough research and real testing of the flows
- Possible restructuring of the information architecture
- Major rewrite or complete rebuild of the chosen sections
- Rich examples, edge cases, and strong progressive disclosure

This is **depth on a defined surface**.

<Tip>
  When a Health Check has already been completed, the research phase is largely done. In that case I re-quote the Focused Section Rebuild at a lower fixed price that reflects the work already completed.
</Tip>

### 3. Docs Partnership (Ongoing)

Part-time, continuous responsibility for keeping a defined area of the documentation accurate and useful as the product moves.

### 4. Paid Discovery

A short, fixed engagement that produces a clear recommendation of the highest-value next step (usually a Health Check or a Focused Section Rebuild). The fee is credited if we proceed.

## How I work

<Steps>
  <Step title="Briefing / Discovery">
    We clarify goals, current state, target audience, and constraints. For larger or unclear scopes I recommend starting with Paid Discovery.
  </Step>
  <Step title="Access & Research">
    I get temporary access to the docs repository (and related code when needed) and study the current state.
  </Step>
  <Step title="Implementation">
    I work directly in the repository and open pull requests with clear descriptions.
  </Step>
  <Step title="Feedback & Iteration">
    One structured revision round is included. Additional rounds or significant scope changes may carry a revision fee.
  </Step>
  <Step title="Delivery & Next Steps">
    Work is merged (or ready to merge). I provide a short summary and, when relevant, a clear recommendation for the next highest-value engagement.
  </Step>
</Steps>

Most Health Checks take 1–2 weeks.
Focused Section Rebuilds usually take 2–4 weeks depending on scope.

Urgent work can be prioritized under a **prioritization fee**.
